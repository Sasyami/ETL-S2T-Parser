# Operation-skills coordinator

Каждый профиль разделён по владельцам решения. Downstream только декомпозирует
чтение, planner выбирает вызовы, observer принимает evidence, upstream decision
проверяет достаточность, upstream answer выполняет итоговый анализ.

Planner и observer получают профиль всей операции при каждом worker, но
исполняют и проверяют только текущую `worker task`. Они не добавляют в worker
остальные чтения operation-плана. Для observer `complete` означает полноту
текущей task; совокупную полноту всех workers проверяет только upstream decision.

## Совместимость колонок

### Downstream plan

- При явно заданном `file_id` создай одну задачу чтения точной пары. При полном
  `filename` сначала создай задачу точного разрешения файла, затем одну задачу
  пары с `file_id` из принятого результата. Сохрани обе роли, оба `table_name`,
  оба `column_name` и один сравниваемый атрибут. Идентификатор допустим только
  из запроса или принятого результата; не дроби пару с потерей второй стороны.

### Planner

- В задаче разрешения файла прочитай точное полное `filename` и заверши worker.
  В зависимой задаче пары сначала прочитай принятый результат разрешения и
  используй возвращённый им `file_id`. Для нескольких файлов выбери результат,
  соответствующий имени текущей пары.
- Если в палитре есть exact pair-reader с обязательными пятью идентификаторами,
  прочитай обе стороны одним вызовом. Иначе сделай два точных ролевых чтения.
  Во всех случаях сохрани заданные `file_id`, source/target `table_name` и
  `column_name`; не заменяй чтение готовых атрибутов фильтром по ожидаемому
  `data_type`, `primary_key` или `not_null`.

### Observer

- Результат разрешения принимай только при точном совпадении `filename` и одном
  однозначном `file_id`. Если исходный scope задан именем, каталоговая пара
  релевантна только с этим разрешённым идентификатором.
- Pair-result принимай только при всех пяти точных args и наличии строк обеих
  `column_role`; два раздельных результата — только при точной роли и всех args
  каждой стороны. Потерянный `file_id`, отсутствующая сторона либо совпадение
  имени без запрошенного атрибута оставляют gap. Пустой точный результат
  означает «неизвестно», а не `false`.

### Upstream decision

- Для исходного `filename` дополнительно требуется evidence его однозначного
  разрешения; идентификатор пары должен совпадать с ним. `pass` допустим при
  одном pair-evidence с обеими ролями либо при двух точных
  ролевых evidence. В обоих вариантах должны быть подтверждены все пять
  идентификаторов и значения одного и того же атрибута. Не переноси значение
  между одноимёнными колонками.

### Upstream answer

- Сравнивай только одинаковые атрибуты. `not_null=true` запрещает `NULL`,
  `not_null=false` допускает его; совместимость типа, nullable и признака ключа
  — разные выводы. Верни фактические source/target-значения; неизвестное не
  нормализуй и не угадывай.

## Анализ SQL-рисков

### Downstream plan

- Планируй только чтение фактов, а не задачи оценки риска. Всегда запрашивай
  полный S2T-маппинг точной `source_table → target_table` с фактическим SQL или
  правилом: он нужен для анализа отсечения, размножения, схлопывания и изменения
  значений.
- Для вопроса о потере, размножении, схлопывании или дубликатах в самой
  трансформации полный mapping достаточен для структурного либо условного
  вывода о кардинальности. Не добавляй metadata только ради проверки ключей,
  nullable, назначения уровня риска или снятия корректной условности.
- Добавь отдельное чтение полных column metadata, только если `original_task`
  прямо требует анализ constraint rejection, nullable/type/key-совместимости
  либо точный вывод, зависящий от каталожных атрибутов. Тогда прочитай обе
  названные endpoint-таблицы одним batch, сохрани обе роли и все структурные
  атрибуты; если `file_id` не задан, используй `file_scope="all"`. Не сокращай
  metadata-задачу до одной стороны.
- Стратегию записи (`INSERT`, `MERGE`, `UPSERT`, overwrite, обработку конфликта)
  можно анализировать только из явно доступного источника; не создавай для неё
  вымышленное чтение. Не создавай transformation ID и не угадывай file_id из
  имени.

### Planner

- Для mapping-task используй единственный directed mapping-reader только с
  обязательными `source_table` и `target_table`; не сужай результат по полю,
  условию или предполагаемому риску.
- Для metadata-task прочитай одним batch ровно весь заданный набор endpoint-
  таблиц и ролей, без фильтра по ожидаемым `data_type`, `primary_key` или
  `not_null`. Если task требует обе таблицы, результат одной таблицы неполон.
  Сохрани заданный file scope; при `file_scope="all"` не выводи file_id из имени.
- Выполняй только чтение текущей task. Не заменяй отсутствующую write strategy
  наличием target PK, не используй `transformation_id` и не ограничивай
  глобальную S2T файловым scope. Planner получает факты, но не назначает уровень
  риска.

### Observer

- Проверяй только scope и полноту чтения текущей task, не оценивай безопасность.
  Mapping принимай при обеих точных таблицах, отсутствии field/ID narrowing,
  полном фактическом правиле и `truncated=false`.
- Metadata принимай только для точного заданного file scope, полного набора
  запрошенных endpoint-таблиц и без фильтра по предполагаемому PK, NOT NULL или
  типу. Уменьшенная task, потерявшая одну исходно названную endpoint-таблицу, не
  делает односторонний результат полным для этой операции.
- Пустой exact metadata-result означает лишь отсутствие строк в сохранённом
  каталоге, а не отсутствие ограничений во внешней СУБД. Не требуй остальные
  evidence операции внутри одного worker и не отклоняй полный результат только
  потому, что он допускает условный вывод. Вызов по ID нерелевантен.

### Upstream decision

- Оценивай достаточность только относительно `original_task`: не требуй больше
  evidence, чем необходимо для достоверного ответа на исходный вопрос. Если
  принятое evidence уже позволяет достоверный условный вывод с явно указанными
  границами, верни `pass`. Дополнительные данные, которые только уточняют вывод
  или снимают его условность, не являются обязательным условием `pass`.
  `reroute` допустим лишь тогда, когда без конкретного отсутствующего факта
  нельзя правдиво ответить на запрошенную часть исходной задачи.
- Оценивай evidence отдельно по слоям. Exact mapping с полным правилом достаточен
  для фактического или условного вывода о SQL-кардинальности. Для подтверждённого
  вывода о rejection нужны фактическое target-ограничение и соответствующая
  source metadata либо выражение; target-only evidence подтверждает ограничение,
  но не безопасность source. Для write semantics нужен явный write statement
  или стратегия — PK её не заменяет.
- Условный вывод достаточен, только когда назван конкретный подтверждённый
  механизм и точный неизвестный фактор: например, подтверждён JOIN, но не
  уникальность полного набора правых join keys. Абстрактная возможность без
  связи с evidence недостаточна. Не делай `reroute` ради оценки вероятности,
  назначения уровня low/high или снятия уже корректной условности.
- Отсутствующий фактор сохраняй как `не оценено`, а не как фактор снижения
  риска. Нулевой mapping подтверждает отсутствие только при точном pair-вызове.
- Если metadata принята, сопоставляй её только с фактическими `file_id` строк
  mapping; при нескольких версиях не смешивай их атрибуты и сохрани конфликт.
  Пустой каталог при `file_scope="all"` означает отсутствие данных, но не
  отсутствие ограничения в самой внешней СУБД.

### Upstream answer

- Перед общим выводом независимо оцени только относящиеся к `original_task`
  слои: (1) отсечение входных строк самим SQL; (2) размножение или схлопывание
  строк; (3) rejection результата ограничениями загрузки; (4) изменение
  значений; (5) write semantics — append/overwrite/merge/upsert/conflict handling.
  Вывод одного слоя не переноси на другие.
- Для каждого слоя используй один эпистемический статус: `подтверждено`,
  `условно`, `не обнаружено в полном рассмотренном evidence` или `не оценено`.
  Укажи подтверждённый механизм, его эффект, условие эффекта и границу evidence.
  `Не оценено` никогда не является фактором снижения риска. Не назначай
  «низкий/средний/высокий» уровень без заданной шкалы и evidence для всех её
  факторов; при неизвестном существенном слое общий вывод остаётся условным.
- Различай итоговые `WHERE`, `HAVING`, `QUALIFY`, условия `JOIN ON` и выражения
  значений. Predicate удаляет строку или группу при `FALSE` либо `UNKNOWN`.
  `INNER JOIN` удаляет строки без совпадения. `LEFT JOIN ... ON` сам не удаляет
  левую строку; последующий `WHERE` по правой стороне анализируй по точному
  predicate и не объявляй автоматически INNER JOIN. `WHERE 1=1` не фильтрует.
  `LIMIT`, `EXCEPT`, `INTERSECT`, `DISTINCT`, `GROUP BY` и дедупликацию оценивай
  как отдельные механизмы ограничения или схлопывания.
- JOIN размножает строку по числу совпадений. Без evidence уникальности полного
  набора правых join keys риск размножения условный. Прямой field mapping не
  доказывает кардинальность 1:1 и не является фактором снижения этого риска.
  Raw-дубликаты S2T-строк сами по себе не доказывают дубли данных.
- Для rejection сопоставляй только точную пару
  `source_table.source_field → target_table.target_field`. Nullable source при
  `target not_null=true` означает условный rejection при фактическом `NULL`.
  Если target-ограничение подтверждено, а source-атрибут неизвестен, риск не
  оценён и его нельзя назвать минимальным. Несовпадение типов означает условный
  conversion/rejection risk до проверки точного преобразования и значений.
- `CASE`, `COALESCE`, `CAST` и арифметика изменяют значения, но сами по себе не
  фильтруют строки. Target PK/UNIQUE может привести к конфликту записи, однако
  не доказывает кардинальность SELECT, `UPSERT`, идемпотентность или
  дедупликацию. Если write statement отсутствует, обработка конфликта остаётся
  `не оценено`; не придумывай режим записи.
- Отсутствие механизма в полном mapping позволяет сказать только «не обнаружено
  в рассмотренной трансформации», но не «невозможно во всём pipeline». В конце
  отдельно назови: что доказано, что остаётся условным и какой конкретный факт
  снимет условность. Не объявляй трансформацию отсутствующей по вызову с
  неподтверждённым ID.

## Покрытие маппинга

### Downstream plan

- Если scope задан одним или несколькими полными `filename`, первым шагом
  разреши все имена. Для target-покрытия затем запланируй:
  (1) точный `target_columns` разрешённых `file_id`/`table_name` с фактическим
  фильтром `not_null=true`; (2) все
  `target_field` глобальной S2T для той же `target_table`. Для source-покрытия
  зеркально используй точный source-reader. Не смешивай эти множества в одной
  задаче и не заставляй upstream повторно фильтровать полный каталог.

### Planner

- В задаче разрешения прочитай точное `filename` и заверши worker. В зависимой
  catalog-task сначала прочитай принятый результат разрешения и используй его
  `file_id`. При нескольких файлах используй соответствие для нужного имени.
- Если текущая task просит обязательный target-каталог, используй точный
  role-reader с `file_id=<file_id>`, `table_name=<target_table>` и
  `not_null=true`; он должен вернуть все совпадения без limit. Если task просит
  S2T, читай exact target-role reader точной таблицы. Не выполняй
  противоположную task в том же worker. Для source-задачи роли зеркальны.
  File scope применяется к каталогу, но не к глобальной S2T.

### Observer

- Результат разрешения принимай только при точном `filename` и одном `file_id`.
  При исходном filename catalog-result релевантен только для этого ID.
- Принимай полное множество, назначенное текущей task. Для catalog-task result
  релевантен только при exact target-role, `file_id`, `table_name` и
  `not_null=true`; полный нефильтрованный каталог не заменяет это множество.
  Для S2T-task result без exact target-role/table нерелевантен. Не требуй
  второе множество внутри этого worker. `truncated=true` оставляет gap.
  Исходные дубликаты строк сохраняются, но множество имён строится отдельно.

### Upstream decision

- При исходном `filename` сначала требуется его однозначное разрешение, а
  catalog evidence должен использовать возвращённый ID. `pass` требует
  одновременно exact отфильтрованный каталог обязательных
  колонок заданного file_id/table и глобальные S2T-поля той же роли/table.
  Не требуй file_id-фильтр или совпадение file_id от глобальной S2T. Evidence
  другой catalog-роли/файла не закрывает требование. Точный пустой S2T-результат
  является данными; запрос с потерянным catalog-фильтром — нет.

### Upstream answer

- Построй множества технических имён: `mandatory` — все `column_name` принятого
  exact результата с `not_null=true`, `mapped` — `target_field` либо
  `source_field` той же роли. Ответная разность равна `mandatory − mapped`;
  `mandatory_fields_count` — размер первого множества,
  `mandatory_fields_without_mapping_count` и список — размер и элементы одной
  и той же разности. Не переноси поля противоположной роли.

## Проектирование проверки

### Downstream plan

- Запланируй три независимых чтения: (1) точный S2T-маппинг заданной пары;
  (2) все S2T-строки точной `target_table`, чтобы не потерять поля из
  дополнительных источников; (3) role-fixed target-каталог точных
  `file_id`/`table_name`. Literal file_id обязательно сохрани в catalog-task.
  Фактические метрики внешней СУБД не выполняй.

### Planner

- Выполни только чтение текущей task: пару — directed mapping-reader с
  обязательными `source_table` и `target_table` (других narrowing args нет);
  target-спецификацию — exact target-role reader; target-каталог — role-fixed
  reader с обязательными `file_id=<file_id>` и `table_name=<target_table>`, без
  атрибутного фильтра. Не собирай остальные два набора в этом worker и не
  придумывай ID, поля, ключи или служебные имена.

### Observer

- Проверяй только назначенный текущей task набор. Pair evidence принимается при
  обоих именах таблиц и без придуманных field-args; target-wide evidence — при
  exact target-role/table; catalog evidence — при точных file scope/table и
  target-рядах. `complete` требует полноту одного назначенного набора, а не всех
  трёх; совокупность проверит upstream decision.

### Upstream decision

- `pass` допустим только при полном pair-mapping, всех строках точной
  `target_table` и точном target-каталоге заданного file_id/table. Не требуй
  file_id-фильтр или совпадение file_id от глобальной S2T.
  Если target-wide строки содержат разные несвязанные правила без стабильного
  group-id, не группируй их по сходству текста: сохрани неоднозначность для
  ответа. Каждый идентификатор будущего SQL должен быть подтверждён либо явно
  оставлен placeholder.

### Upstream answer

- Для каждой проверки дай цель, SQL-шаблон и однозначный критерий прохождения;
  не выдавай шаблон за выполненную проверку. Ожидаемое количество строк выводи
  только как `COUNT(*)` над дословным сохранённым SELECT в подзапросе: не
  переписывай JOIN, не переноси `LEFT JOIN ON` в `WHERE`/`NOT EXISTS` и сохрани
  возможное размножение строк. Шаблон, который считает только raw source-table,
  недействителен. Scope конкретного запуска оставь
  `<LOAD_SCOPE_PREDICATE>`.
- Проверку null-rate применяй только к колонкам с подтверждённым
  `not_null=true`, уникальность — только к подтверждённому ключу. Полевые
  проверки строй по каждой точной S2T-строке этой `target_table`, включая
  дополнительные source-таблицы. Сохрани raw multiplicity: одинаковые строки
  можно компактно представить только с точным числом occurrences, не молча
  схлопывать. Не склеивай строки по похожести rule и не заимствуй выражение из
  другой target-таблицы. Не придумывай batch-колонку:
  неизвестный scope нагрузки оставляй `<LOAD_SCOPE_PREDICATE>`. В SQL-критерии
  уникальности повтори выражение ключа в `HAVING COUNT(*) > 1`, а не alias.
- Проверка значения не должна соединять target с source по самому проверяемому
  равенству и затем использовать `LIMIT`: это тавтологичная выборка, а не
  полный контроль. Сначала построй ожидаемые строки дословным сохранённым SQL,
  затем верни все несовпадения; критерий — ноль mismatches. Source-field каждой
  target-колонки бери только из её точной S2T-строки: JOIN-проекция соседнего
  маппинга не заменяет эту пару.
