# Правила upstream-анализа

Применяй только правила, относящиеся к original_task и принятым evidence.

## Компактные табличные evidence

- При `row_format=named_records_with_dictionary_refs` каждая row уже содержит
  явные имена полей. Только для полей из `dictionaries` целое значение является
  0-based индексом точного исходного значения в словаре.
- Dictionary-индексы — transport references, не database/group ID. Одна row
  соответствует одной исходной строке;
  не схлопывай одинаковые occurrences и не группируй их по словарному индексу.
- Полнота означает одновременно `returned_rows == len(rows)` и
  `truncated=false`; сначала разреши словарные ссылки, затем фильтруй строки
  точным равенством по фактическим полям и атрибутам.

## SQL и S2T

- Анализируй только фактический `transformation_rule` или SQL из evidence.
- В объяснении фактического правила называй присутствующие `JOIN`, `WHERE`,
  `CASE`, `GROUP BY` и оконные функции. NULL, пустая строка и ровно «-» означают
  прямое правило.
- Сохраняй точные source/target-роли. `CASE`, `COALESCE`, `CAST` и literal сами
  по себе не подтверждают фильтрацию строк.
- Полевой маппинг задаёт конкретная S2T-строка
  `source_table.source_field → target_table.target_field`. Выражение или колонка
  в общем табличном SQL не означает, что она заполняет произвольное target-поле;
  не подменяй точную S2T-пару соседним выражением из того же SELECT.
- `WHERE 1=1` не фильтрует. `LEFT JOIN ... ON p` не удаляет левую строку, но
  может размножить её без доказанной уникальности справа; `ON TRUE AND p`
  эквивалентно `ON p`. `UNION ALL` сохраняет дубли, `UNION` удаляет.
- Прямой value-mapping поля не доказывает кардинальность строк 1:1. PK/UNIQUE в
  target может вызвать конфликт, но не доказывает `UPSERT` или дедупликацию без
  явной стратегии записи в evidence.
- Одинаковые target и правило при разных source_field могут быть входами одной
  трансформации. Полные одинаковые строки не являются разными правилами, но их
  raw occurrence-count сохраняется и не замалчивается.

## Сравнение и lineage

- Сравнивай один набор признаков отдельно по каждому объекту; порядок объектов
  не задаёт source/target-направление. Не переноси факт между объектами.
- Для lineage сохраняй физический порядок
  `source_table.source_field → target_table.target_field`; готовый
  `text_diagram` переноси дословно.
- Neo4j — проекция lineage. Отсутствие связи в ней не отменяет факты SQLite.
