# Правила upstream-анализа

Применяй только правила, относящиеся к original_task и принятым evidence.

## SQL и S2T

- Анализируй только фактический `transformation_rule` или SQL из evidence.
  В объяснении называй присутствующие `JOIN`, `WHERE`, `CASE`, `GROUP BY` и
  оконные функции. NULL, пустая строка и ровно «-» означают прямое правило.
- Сохраняй точные source/target-роли. Отдельно описывай изменение значения и
  изменение множества строк: `CASE`, `COALESCE`, `CAST` и literal выбирают или
  преобразуют значение, но сами по себе не фильтруют строки.
- Строки могут сокращать `WHERE`, `HAVING`, `INNER JOIN`, `SEMI/ANTI JOIN` и
  условия, превращающие внешний JOIN во внутренний; `WHERE 1=1` не фильтрует.
  Условие правой таблицы в `ON` у `LEFT JOIN` само по себе не удаляет левую
  строку, в отличие от последующего фильтра по nullable-полю правой стороны.
- Риск размножения строк определяется кардинальностью JOIN. `DISTINCT`,
  `GROUP BY` и фильтр по `row_number()` могут устранять дубли; окно без фильтра
  не является дедупликацией. `UNION ALL` сохраняет дубли, `UNION` удаляет.
- Одинаковые target и правило при разных source_field могут быть входами одной
  трансформации. Полные одинаковые строки не являются разными правилами.
- По SQL нельзя утверждать фактическое наличие NULL, дублей или потерь в данных.

## Сравнение и lineage

- Сравнивай один набор признаков отдельно по каждому объекту; порядок объектов
  не задаёт source/target-направление. Не переноси факт между объектами.
- Для lineage сохраняй физический порядок
  `source_table.source_field → target_table.target_field`; готовый
  `text_diagram` переноси дословно.
- Neo4j — проекция lineage. Отсутствие связи в ней не отменяет факты SQLite.
